# 內容營運：子部落格與內容管理

技術基礎（SEO）與機器可讀性（AEO、GEO）到位之後，剩下的工作只有一件：**持續產出值得被引用
的句子，並在它們過時時更新。** 代操公司月費的大部分就花在這裡（「每月 N 篇貼文」）。本文件把這件事從
憑感覺變成**流程管線**：蒐集問題 → 簡報 → 撰寫 → 發布關卡 → 更新 → 測量。

內容橫跨全部五條通道。內容在各通道的角色：

| 通道 | 內容的角色 |
|---|---|
| SEO | 可被索引頁面的數量與新鮮度 |
| AEO | 「一個問題 = 一個頁面」的供給來源 |
| GEO | 段落層級的引用素材（主詞＋數字＋基準日＋產出方式） |
| LLMO | 建置過程的紀錄 = 會留在訓練語料裡的表面 |
| TW | 「自有網域＋外部平台」雙軌中，外部平台（方格子、痞客邦等）那一側 |

## 0. 診斷：內容現況

```bash
# 有沒有部落格，爬蟲看不看得到
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/blog
curl -sL https://example.com/blog | grep -c '<article\|<h2'          # 列表是否為 SSR
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/feed.xml # RSS/Atom 是否存在
curl -sL https://example.com/sitemap.xml | grep -c '/blog/'           # 網站地圖內的文章數
curl -sL https://example.com/sitemap.xml | grep -o '<lastmod>[^<]*' | sort | tail -1  # 最近一次發布
# 抽樣一篇：第一段是否直接作答、有沒有 Article LD
curl -sL https://example.com/blog/some-post | grep -o '"@type":"[A-Za-z]*"' | sort | uniq -c
```

- [ ] 建立**內容盤點表**：以單篇文章為單位，欄位為 URL · 標題 · 目標問題 · 類型 · 發布日 ·
      最後更新 · 近 28 日曝光／點擊 · 狀態。沒有這張表，之後所有判斷都是憑感覺
- [ ] 從盤點表數三個數字：① 沒有目標問題的文章 ② 超過 90 天沒更新的文章
      ③ 曝光為 0 的文章。這三個數字就是診斷結果

評分表佐證範例：「部落格 34 篇、對應問題 0 篇、近 90 日發布 0 篇、曝光為 0 的文章 21 篇」。

## 1. 放在哪裡：子部落格的位置

| 選項 | 優點 | 缺點 | 判斷 |
|---|---|---|---|
| **子目錄** `example.com/blog` | 網域權威集中，網站地圖、llms.txt、LD 在同一處管理 | 部署與主應用綁在一起 | 通過：預設選擇 |
| **子網域** `blog.example.com` | 技術堆疊與部署可分離 | 實務上較接近被當成另一個網站，權威被分散 | 僅在主應用無法 SSR 時採用 |
| **外部平台**（方格子 vocus、痞客邦 PIXNET、Medium） | 平台內的曝光與讀者 | 事實的原帳落在別人的網域、無法掌控 canonical、有政策變動風險 | 只當衛星使用（第 7 節） |

原則：**事實的原帳（資料與問題頁面）放在自有網域，外部平台只放摘要加連結的衛星。**

子部落格的技術要求（`references/seo.md` 的精簡版）：

- [ ] SSR/SSG：Markdown → 靜態 HTML 最安全。若使用 CMS，要用 curl 確認渲染結果
- [ ] 每篇文章有獨立的 title、description（以搜尋結果顯示寬度為準，見 `references/seo.md`）與 OG 圖片
- [ ] `Article`（或 `BlogPosting`）JSON-LD：headline · datePublished · dateModified · author ·
      publisher 引用全站的 Organization `@id`（不要每頁重新宣告）
- [ ] `BreadcrumbList` LD 加上可見的麵包屑
- [ ] RSS/Atom 摘要來源：爬蟲、閱讀器與 IndexNow 觸發的共同輸入
- [ ] 網站地圖**自動**納入文章並帶有正確的 lastmod（手動維護的網站地圖一定會漏）
- [ ] 標籤、分類與分頁頁面：文章少於 3 篇的單薄列表設 noindex，
      只讓打算養成樞紐頁的列表保留 index。放著不管，幾百個單薄頁面會耗掉索引預算
- [ ] 文章 URL 只用 slug、不放日期（`/blog/example-earnings-call`），更新後 URL 也不會過時

## 2. 內容模型：單篇文章的中繼資料

每篇文章都備齊下列 frontmatter（或 CMS 欄位）。**頁面渲染與 JSON-LD 都從這單一來源產生**，
就能從根本杜絕可見文字與 LD 不一致：

```yaml
---
title: "範例電子法說會是哪一天"                   # 與 h1 相同
slug: example-earnings-call
question: "範例電子法說會是哪一天"                 # 使用者在搜尋框輸入的原句
answer: "範例電子下一次法說會日期為 YYYY 年 MM 月 DD 日（暫定，以公開資訊觀測站公告為準）。"  # 第一段直接作答，約 40 字
description: "…"                                 # 不被截斷的長度，給人點擊的理由
type: question        # question | data | glossary | buildlog | comparison
datePublished: 2026-09-21
dateModified: 2026-09-21                         # 只在內容實際變更時才更新
data_asof: 2026-09-20                            # 本文數字的基準日
author: { name: "…", url: "/about" }
sources:
  - { name: "公開資訊觀測站", url: "https://mops.twse.com.tw/" }
faq:
  - { q: "法說會是盤中還是盤後舉行", a: "…" }
related: [example-dividend-date, earnings-calendar]
status: published     # draft | review | published | refresh-needed | merged
canonical: https://example.com/blog/example-earnings-call
---
```

- [ ] `question` 為空就不發布：不知道自己在回答哪個問題的文章，不會被抽取成任何問題的答案
- [ ] `answer` 會原樣渲染為本文第一段；只存在於中繼資料、畫面上看不到就無效
- [ ] `data_asof` 會標示在本文數字旁（「截至 2026-09-20」）；沒有基準日的數字會被扣分
- [ ] `faq` 是可見 FAQ 區塊與 FAQPage LD 兩者的單一來源

## 3. 文章類型：會被引用的五種

| 類型 | 形式 | 哪條通道吃這種內容 |
|---|---|---|
| **問題頁面** | 針對一個「○○ 何時／多少／怎麼做」直接作答，附證據表格 | AEO、TW |
| **資料頁面** | 自行產出的數字、穩定的 URL、載明更新週期 | GEO（第一手來源的主體） |
| **名詞定義頁面** | 一句話定義＋比較表＋範例 | AEO（最優先被抽取的形式） |
| **建置紀錄／變更紀錄** | 做了什麼、為什麼、怎麼做，附實測數字 | LLMO（訓練表面）＋E-E-A-T 的「經驗」 |
| **比較頁面** | 以表格為主、標明基準日、不偏袒自家 | AEO、GEO |

不要做的事：
- 不做：新聞改寫、整理別人的數據：引用會被原始出處搶走（`references/geo.md` 第 3 節）
- 不做：關鍵字變體的大量頁面（「○○ 推薦」「○○ 推薦 2026」「○○ 排名」……）：同一個答案的複製品
      會互相瓜分排名，規模變大還可能被判定為「規模化內容濫用」
- 不做：沒有答案的文章：結論是「視情況而定」的文章，沒有任何引擎會引用

## 4. 流程管線

### 4-1. 問題待辦清單

內容行事曆不是「本月主題」，而是**待回答問題的佇列**。來源依序為：

1. GSC 與 Bing Webmaster Tools 的熱門搜尋詞中**沒有專屬頁面的問題**（`references/measure.md` 第 4 節）
2. 有曝光但平均排名落在 5～15 名的問題：已經是候選，只是直接答案或表格偏弱
3. 站內搜尋、客服詢問、客戶提問紀錄
4. Google 自動完成與相關搜尋，加上 Dcard、PTT、Mobile01 的討論串標題（當作使用者真實問法的來源）

用 `content/backlog.md` 管理：

```markdown
| 問題 | 依據 | 類型 | 狀態 | URL |
|---|---|---|---|---|
| 範例電子除息日 | GSC 曝光 1,240・排名 11 | question | draft | |
| 本益比怎麼算 | 自動完成・詢問 3 件 | glossary | backlog | |
```

優先順序：**有曝光且排名低 > 有曝光但沒有專屬頁面 > 推估的新需求**。
只憑推估需求撰寫的文章，排在待辦清單最底部。

### 4-2. 簡報：寫作前的一分鐘

動筆前先填五行。填不出來，代表這篇文章還不能寫：

```
問題：      （搜尋框輸入的原句）
直接答案：  （一句話，約 40 字，含數字與日期）
證據：      （要做成一張表的資料＋基準日＋來源 URL）
子查詢：    （客人真實會問的、AI 可能拆出的；各對應到回答它的段落）
內部連結：  （1 個樞紐頁＋2 篇相關文章／資料頁面）
```

選題依真實需求，FAQ 題數依實際提問決定，不固定湊數。FAQ 和 Schema 在 arXiv 2610.15033
的同站比較中，未觀察到與引用的顯著關聯（單一研究），不代表引用增益。

### 4-3. 撰寫規則：機器可讀

把 `references/aeo.md`、`geo.md` 的句子規則套用到單篇文章：

- [ ] 第一段 = 直接答案。禁止前言、背景、寒暄
- [ ] 段落自立：每一段自帶主詞、數字與基準日（禁止「前面提到的那個數字」）
- [ ] 先想表格：數字有三個以上就用表格，不用散文
- [ ] H2 直接使用子問題原句（`## 法說會是盤中還是盤後舉行`）
- [ ] 長度以答案所需為準。「2,000 字以上」之類的規則會養出灌水，灌水會把直接答案埋掉
- [ ] 每個數字都附來源與基準日。若是自行算出的值，補一行算法
- [ ] **AI 初稿政策**：允許用 AI 產生初稿，但必須 ① 每個數字都對照原始出處 ② 由真人審稿並以作者署名
      ③ 禁止大量自動發布。搜尋引擎的標準不是「誰寫的」而是「有沒有被驗證」；
      未經驗證的 AI 文章，問題不在來源，而在錯誤的數字與空洞的結論
- [ ] 受管制行業（金融、醫療、法律）不寫預測或勸誘型句子，只寫能由資料確定的內容

### 4-4. 發布關卡：全數通過才能發布

- [ ] frontmatter：`question`、`answer`、`data_asof`、`sources` 已填，h1 = title
- [ ] 用 `curl -sL <url>` 確認本文、直接答案與表格都在 HTML 裡（不靠 JS）
- [ ] title、description 獨一無二、長度在範圍內、全站沒有重複
- [ ] 有 Article LD，dateModified = 實際更新日，publisher 引用全站 Organization `@id`
- [ ] FAQ 可見文字 = FAQPage LD（逐字一致）
- [ ] 內部連結：往上（樞紐）1 個＋橫向（相關）2 個以上，失效連結 0 個
- [ ] 圖片 alt、width/height，並確認總容量
- [ ] 已納入網站地圖且 lastmod 正確（部署後用 curl 確認）
- [ ] IndexNow 通知（Bing、Yandex 會使用；Yahoo 奇摩搜尋結果由 Bing 提供，因此一併受惠），內建在發布管線裡
- [ ] 資料頁面或樞紐等級的文章，要在 `llms.txt` 新增項目
- [ ] RSS 已更新
- [ ] 在 Bing Webmaster Tools 提交網址，並在 Google Search Console 做網址審查／要求索引

### 4-5. 發布之後

記錄基準線（發布日、目標問題、目前曝光 0）→ 在盤點表預約**14 天後重新測量**。
依 `references/measure.md` 的迴圈，逐篇文章跑一遍。

## 5. 更新與整理：內容會腐壞

發布不是終點。過時的文章會失去引用，錯誤的文章會折損信任。

**更新觸發條件**：符合任何一項就標為 `status: refresh-needed`：
- 本文數字依據的基準資料有變動（財報發布、價格調整、政策變更）
- 近 28 日曝光比 60 天前下降 30% 以上
- 搜尋詞資料顯示問題的用語改變了（例如「2025 年」→「2026 年」）
- 發現或被通報事實錯誤

**更新規則**：
- [ ] `dateModified` **只在內容實際改變時**才更新；只改日期的手法一旦被偵測到會適得其反
      （`references/aeo.md` E-E-A-T）
- [ ] 文末加一行變更紀錄：「2026-10-30 更新：納入第三季財報」，既是信任訊號也是紀錄
- [ ] 更新過的文章也要重新通過發布關卡（包含重新發送 IndexNow）

**合併與刪除**：
- [ ] 同一個問題有兩篇文章時，把較弱的 **301 + canonical** 導向較強的，較弱的標為 `status: merged`。
      重複的文章會互相瓜分排名
- [ ] 刪除是最後手段：過時的文章先更新或做 301。真的要刪就回傳 410，並從網站地圖移除
- [ ] 若必須更換 URL，301 要永久保留（`references/llmo.md` 第 3 節，模型記住的是那個位址）

**每季盤點檢視**：依狀態統計（published / refresh-needed / merged），並對曝光為 0 的文章做出處置決定。

## 6. 內部連結結構

內容超過幾十篇之後，連結結構就等於爬取優先順序：

- **樞紐 → 輻條 → 資料**：主題樞紐（例如 `/blog/earnings`）→ 問題文章 → 原帳資料頁面
- [ ] 每篇文章有往上連結 1 個（樞紐）＋橫向連結 2 個（相關問題）＋資料頁面連結
- [ ] 錨點文字直接用問題或名詞（禁止「這裡」「這篇文章」），錨點就是目標頁面的主題訊號
- [ ] 孤兒頁面 0 個：只出現在網站地圖、沒有任何地方連過去的文章，爬取優先順序最低
- [ ] 若樞紐頁本身很單薄（只有連結清單），也要放入直接答案、概覽與表格，讓它成為獨立頁面
- [ ] 用 BreadcrumbList LD 加上可見麵包屑，對機器也宣告層級結構

## 7. 外部發布：跨平台轉貼

自有網域是原帳，外部都是衛星。**順序很重要**：先確認自有網域已被索引（1～3 天）再發到外部，
不先搶下原始出處，複製品反而會被當成原稿。

| 平台 | 放什麼 | 不要做 |
|---|---|---|
| 方格子 vocus、痞客邦 PIXNET（外部平台） | 摘要＋觀點＋1～2 個指向自有網域資料頁面的連結 | 整篇本文貼上、連結灌水（`references/tw-local.md` 第 5～6 節） |
| Medium | 能指定 canonical 就放全文，不能就放摘要＋連結 | 沒有 canonical 的全文複製 |
| LINE 官方帳號、Threads、X、LinkedIn | 一個關鍵數字＋連結（這裡既是 LLMO 表面，也是流量入口） | 每篇文章都重複同樣的措辭 |
| GitHub README、建置紀錄 | 做了什麼、怎麼做的、實測結果，用陳述事實的文體 | 宣傳口吻 |

- [ ] **先確認平台編輯器是否支援 Markdown**（例如方格子、痞客邦）：不支援時，貼上 Markdown 草稿，
      `#`、`**`、`|` 會原樣顯示成文字。此時改用編輯器自己的標題、粗體、表格功能重建，
      發布後在手機畫面確認沒有符號外洩
- [ ] 把外部發布的時間記錄在盤點表，哪個管道真的帶來流量，就是從這裡看出來的

## 8. 測量：「每月 N 篇」不是指標

代操報告裡的「本月發布 12 篇」是產出量，不是成效。本技能的指標：

- **被看見或被引用的文章比例**：published 當中，近 28 日曝光 > 0 的篇數／有被 AI 引用的篇數
- 單篇文章的 28 日曝光、點擊、平均排名（每月更新一次盤點表）
- 5～10 個目標問題的 AI 引用 O/X（ChatGPT search、Perplexity、Gemini、Google AI Overviews）
- 待辦清單的消化速度 vs 新增速度：待辦清單見底，就該重新閱讀搜尋詞資料了

訊號 → 下一步行動：

| 訊號 | 行動 |
|---|---|
| 曝光上升、點擊下降 | 調整 title 與 description（`references/seo.md` 第 3 節） |
| 曝光為 0（發布 14 天後） | 檢查索引：網站地圖、noindex、SSR、IndexNow |
| 排名卡在 5～15 名 | 強化直接答案、表格、基準日，增加內部連結 |
| 有曝光、沒有 AI 引用 | 確認有無競爭的原始出處、段落自立性、是否列入 llms.txt |
| 曝光下降 30% | 更新觸發條件（第 5 節） |

回報時，在 `references/measure.md` 第 5 節的格式上加一列**單篇文章的行**：

```
[內容] 發布 6・更新 3・合併 1 | 曝光>0 比例 5/6・AI 引用 2/6 | 待辦清單剩餘 14
```
