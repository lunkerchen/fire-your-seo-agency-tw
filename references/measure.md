# 測量迴圈 — 修完不是結束

代理商服務與這個技能的真正差別就在這裡。代理商會寄來「已完成作業」的報告，
這個技能則是確認**數字有沒有動**。沒有測量的最佳化，只是一種主張。

## 1. 基準線 — 動手修之前先記錄

不記錄變更前的狀態，就永遠無法證明成效：

- Google Search Console：最近 28 天的曝光、點擊、平均排名（依頁面群組）
- Bing Webmaster Tools：搜尋成效（曝光／點擊）與熱門搜尋查詢清單。Yahoo 奇摩搜尋結果由 Bing 提供
  （以 `references/tw-local.md` 第 1 節的並排比對驗證）；但 Bing Webmaster Tools 的成效數字只算 Bing，Yahoo 奇摩帶來的流量要另用分析工具的來源報表確認
- AI 引用：選 5～10 個目標問題，實際丟給 Perplexity、ChatGPT 搜尋、Gemini，並在台灣的實際搜尋中
  確認 Google AI 摘要、AI 模式是否出現，把是否引用你的來源記為 O/X（不要預設某個功能一定可用）
- 索引數量：`site:網域` 的結果數 + GSC 已索引頁面數（Bing 也用 `site:` 確認）
- **AI 爬蟲造訪數**：從伺服器日誌看 GPTBot、PerplexityBot、ClaudeBot 等的造訪趨勢。
  爬蟲先來，引用才會來 — 這是比引用更早變動的領先指標

```bash
# 從存取日誌統計 AI 爬蟲造訪數（領先指標）
grep -iE 'GPTBot|OAI-SearchBot|ChatGPT-User|ClaudeBot|Claude-User|PerplexityBot' access.log \
  | awk '{print $1}' | wc -l
# 如果拿不到日誌：改用 Cloudflare、Vercel 等託管後台的機器人流量分類
```

在地面向的測量（Google 商家檔案、論壇引用等）見 `references/tw-local.md` 第 7 節。

## 2. 重新測量的時程 — 屬於作業的一部分

- 搜尋反映變更有時間差：預設**變更後 14 天重新測量**，
  並考量統計延遲，比較時要排除最近 2～3 天
- 不要把重新測量交給「記憶」— 排進行程，或請代理人設提醒。
  用這個技能完成作業的話，在報告中寫明重新測量的日期，就是完成的條件

## 3. 過時資料陷阱

> **過時的資料會通過所有下限檢查。**

只確認指標「不是 0」的監控，就算數值已經好幾天沒更新也會放行。
建置測量管線時，要監控的是**數值的日期**，而不是數值 —
「最後更新超過 N 天就不顯示該指標」是安全的預設值。

## 4. 怎麼讀數字

- **先看曝光，再看點擊**：結構改善的第一個訊號是曝光增加。點擊（CTR）要等標題、描述的
  改善跟上才會動。如果只有曝光增加而 CTR 偏低，下一步就是改 meta
- **週末下滑是正常的**：偏平日性質的主題（商業、金融）在週末曝光會降下來。
  這種模式反而是真實需求的證據
- **搜尋查詢清單就是路線圖**：Bing Webmaster Tools 與 GSC 的熱門查詢，就是「人們實際打的
  問題」清單。前段查詢中沒有專用落地頁的問題 = 下一個要做的頁面

## 5. 報告格式

```
[基準線] 8/1~8/28：曝光 12,400 · 點擊 180 · AI 引用 0/8 個問題
[變更] 8/29：意圖落地頁 6 種 + llms.txt + FAQ LD
[預約重新測量] 9/12
[重新測量結果] 曝光 31,000（+150%）· 點擊 610 · AI 引用 3/8  ← 要有這一行才算完成
```
